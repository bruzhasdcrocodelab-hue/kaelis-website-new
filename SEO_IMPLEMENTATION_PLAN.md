# SEO: SSR, индексация и кэширование Kaelis

## Summary

- Заменить клиентскую маршрутизацию через `LocalizedPages` на серверный рендеринг публичных страниц; интерактивный выбор карт и AI-ответ оставить клиентскими.
- Единым источником допустимых SEO-маршрутов сделать `src/lib/seo/content.json`: сейчас в нём по 75 tarot-маршрутов для `en`, `ru`, `uk`. Страница, отсутствующая в этом справочнике, всегда возвращает 404.
- Использовать существующий API только для публичного каталога/описаний и интерактива; не менять backend и его контракт.

## Задачи 1–2: robots.txt и sitemap.xml — выполнено

- Создать `src/app/robots.ts` через `MetadataRoute.Robots`: `Allow: /`, закрыть `/api/` и служебные пути (`/api/admin/`, `/api/private/`, `/api/internal/`), но явно разрешить используемые публичные API `/api/kaelis/user/anonymous`, `/api/kaelis/tarot/`, `/api/kaelis/configuration` и `/api/kaelis/broadcasting/auth`; добавить абсолютный URL sitemap из `NEXT_PUBLIC_SITE_URL`.
- Создать `src/app/sitemap.ts`: включить для каждого логического маршрута главную, `/tarot` и все разрешённые маршруты раскладов во всех трёх URL-локалях (`en`, `ru`, `ua`); у каждой записи задать `alternates.languages` для `en`, `ru`, `uk` и `x-default`.
- Статические metadata routes имеют приоритет над `[locale]`; дополнительно сохранить в locale-layout строгую проверку `isUrlLocale`, чтобы файловые и неизвестные URL не становились страницами.
- Риск: добавление нового расклада в API требует одновременного добавления его SEO-записи во все три локали, иначе он намеренно не будет индексироваться и вернёт 404.

## Задачи 3–4: 404 и канонический регистр — выполнено

- В `src/proxy.ts` нормализовать URL до рендеринга:
  - при уже корректном locale-prefix заглавные сегменты маршрута, например `/ru/tarot/DREAMS`, перенаправлять 308 на полностью нижний регистр;
  - обработка регистра locale, `uk` и неподдерживаемых locale остаётся в задаче 7 и не входит в этот этап.
- В `src/app/[locale]/tarot/[...slug]/page.tsx` и его `generateMetadata` использовать единый resolver допустимых путей из SEO-справочника. Неизвестные, лишние или неканонические slug вызывать через `notFound()`, без canonical/hreflang.
- Дополнить `tests/routing-seo.test.mjs` сценариями resolver и нормализации регистра для `DREAMS`.

## Задачи 5–6: серверный HTML, контент и ссылки — выполнено

- Перенести корневой layout из `src/app/layout.tsx` в `src/app/[locale]/layout.tsx`, сделав `[locale]` root-параметром. Убрать чтение `headers()` для определения языка: `<html lang>` должен строиться из параметра маршрута, чтобы не переводить все страницы в dynamic rendering и чтобы 404 имела корректный язык.
- Убрать вывод страниц из клиентского `src/components/LocalizedPages.tsx`. Route-файлы главной, хаба и расклада должны сами рендерить страницу с серверными данными и передавать клиентским компонентам только состояние, нужное для интерактива.
- Выделить серверный публичный catalog loader отдельно от браузерного `src/lib/api.ts`: он получает анонимный токен у текущего `NEXT_PUBLIC_BACKEND_ORIGIN`, загружает категории и spreads с теми же заголовками/валидацией и используется только при build/ISR. Браузерный flow, гостевая сессия, WebSocket и генерация AI-расклада не меняются.
- На странице расклада отрендерить в исходном HTML ровно один `h1` из `src/lib/seo/content.json`, lead/описание из публичных API-полей (`site_description`/`description`), доступные сведения о раскладе и хлебные крошки «Главная → Расклады Таро → …». Интерактивный `CategoryTopBlock` оставить клиентским и показывать его loading-state только внутри этого блока.
- На `/[locale]/tarot` серверно вывести обычные ссылки на все категории и доступные spreads через `next/link`; на главной серверно добавить ссылки на основные расклады из существующей карты `HOME_CARDS`.
- FAQ и описания позиций добавлять в серверный HTML только при наличии структурированных локальных данных. API по текущей спецификации отдаёт описание расклада и matrix, но не даёт SEO-FAQ/тексты позиций; их создание — редакционная зависимость, а не задача backend.
- Проверить серверный HTML без JavaScript: H1, текст и ссылки присутствуют в response body; после гидратации интерактивное создание расклада продолжает обращаться к `/api/kaelis/tarot*`, `/configuration`, `/chat/*` и WebSocket.

## Задача 7: локали — выполнено

- Сохранить соответствие URL `ua` ↔ языку интерфейса `uk` в `src/lib/routing.ts`; canonical и sitemap использовать `ua`, hreflang — `uk`.
- Нормализовать URL-локали permanent 308: `EN`/`RU`/`UA` приводить к нижнему регистру, а `uk` (в любом регистре) — к `ua`; одновременно канонизировать регистр пути.
- Явный корректный locale никогда не заменять значением cookie или `Accept-Language`.
- Bare URL (`/`, а также существующие пути без locale) продолжает перенаправляться на согласованный locale; неподдерживаемый locale-подобный префикс permanent 308 перенаправлять на `/en/<остаток-пути>`, не сохраняя его в target.
- Дополнить unit-тесты проверками нормализации `RU`/`UK` и распознавания неподдерживаемых locale-префиксов; проверить в dev-сервере 200 для явного `/en` с противоречащими cookie/заголовком, 308 для `/RU`, `/uk`, `/es` и 307 для bare URL.

## Задачи 8–9: metadata, Open Graph и JSON-LD — выполнено

- Расширить тип и данные `src/lib/seo/content.json`/`index.ts` полями SEO-контента, сохранив текущие title/description/H1 как источник. Для каждого маршрута metadata формировать только после успешного resolver.
- Заменить шаблонные description с эмодзи на локализованные значения длиной до 160 символов; title — до 60. Для `/ru/tarot/dreams` использовать значения из ТЗ:
  - title: «Сонник ИИ онлайн — толкование снов по картам Таро | Kaelis»;
  - description: «Опишите сон — нейросеть Kaelis сделает расклад Таро и расшифрует его значение. Бесплатно, онлайн, без регистрации.»;
  - H1: «Толкование снов с помощью Таро и искусственного интеллекта».
- В `pageMetadata` добавить `openGraph` и `twitter`: title, description, canonical `url`, locale, `twitter.card = summary_large_image` и единое изображение.
- Добавить временный статический файл `public/images/seo/og-placeholder-1200x630.png` размером 1200×630; его URL закрепить в metadata как единственную точку замены будущего брендового изображения.
- В locale root layout вывести JSON-LD `Organization` и `WebSite`; на страницах раскладов — `BreadcrumbList`; `FAQPage` — только когда у записи действительно есть FAQ. Сериализовать JSON-LD безопасно для `<script>`.
- Добавить локализованный `not-found.tsx` под `[locale]`, чтобы 404 использовала текущий `lang` и не публиковала неверные canonical/hreflang.

## Задача 10: ISR и CDN

- Для locale-layout и публичных страниц экспортировать `generateStaticParams` для `en`, `ru`, `ua`; для `/tarot` и `/tarot/[...slug]` сгенерировать полный разрешённый список маршрутов.
- Установить `revalidate = 3600` для хаба и раскладов, а публичные server fetch выполнять с тем же временем revalidation. Не включать новый Cache Components режим: обычная ISR-схема достаточна и не затрагивает существующий client flow.
- Исключить из layout все request-time API (`headers`, `cookies`) на индексируемых путях; locale брать из root parameter. Это является обязательным условием CDN-кэша вместо `private, no-store`.
- Риск: API должен быть доступен на build и ISR. При ошибке загрузки публичного каталога build/revalidation должен завершаться ошибкой, а не выпускать пустую индексируемую страницу.

## Test plan

- Unit-тесты resolver: каждый маршрут из SEO-справочника валиден во всех локалях; неизвестные slug/дополнительные сегменты невалидны.
- Тесты metadata: canonical, hreflang, OG/Twitter, ограничения длины, отсутствие эмодзи в обновлённых description, JSON-LD и отсутствие FAQPage без FAQ.
- Тесты metadata routes: `/robots.txt` и `/sitemap.xml` возвращают 200, sitemap содержит все локали и hreflang; robots разрешает фактически используемые публичные API.
- Интеграционная проверка production/staging через `curl` без JS: корректные URL — 200 с H1 и контентом; invalid slug — 404; URL в ином регистре — 308; `/RU/...` и `/uk/...` нормализуются; `/es/...` — 404.
- После двух запросов к страницам хаба и расклада проверить ISR/CDN-заголовки: отсутствует `private, no-store`, последующий запрос даёт cache hit согласно Vercel.
- Прогнать существующие тесты каталога, чтения и locale-switching, чтобы серверное начальное состояние не изменило интерактивный flow.

## Assumptions

- `NEXT_PUBLIC_BACKEND_ORIGIN=https://app.kaelisai.com` имеет ту же публичную API-структуру, что и проверенный staging.
- В sitemap попадают только маршруты, для которых существуют все локализованные SEO-данные.
- Пока редакция не предоставила FAQ и тексты позиций, эти блоки не будут искусственно генерироваться; обязательный серверный контент состоит из H1, описания расклада, хлебных крошек и ссылок.
